# エージェント間連携のルール

目的は、前工程が未確認のまま後工程が進むこと、担当の重複、訂正前の成果による完了を減らすことです。文章での指示とアプリによる実行制御を分けます。順序を守ったことだけで、調査内容や成果物の正しさが保証されるわけではありません。

## PMが最初に決めること

PMは各担当の役割、必要な入力、出力先、受入基準を明記します。たとえば天気をExcelにまとめる依頼なら、調査担当は対象地域・日付・出典を確定し、表の作成担当は承認された調査結果を入力とし、PMは保存と読み戻しの証拠を確認します。不要な地域・期間の取得や、同じファイルの同時編集を避けるよう作業を分けます。

これはモデルへ求める作業規律です。アプリが依頼文を理解して最適な分担や受入基準を自動生成・検証する機能ではありません。

## 一方向の工程を依存関係でつなぐ

1. PMが先行ワーカーを作り、返された実際の担当IDを控えます。
2. 後続ワーカーの `spawn_worker` に `depends_on` として先行担当IDの配列を渡します。指定できるのは、同じ作業で同じPMが管理する既存ワーカーのIDで、最大16件・重複なしです。未作成の担当や自分自身を指す循環は作れません。
3. 先行ワーカーが `finish_work` で正式報告します。PMはその現在版を受け取り、文脈へ取り込んでから `review_worker_report` で `accept` します。
4. 必要な先行報告がすべて承認されてから、後続ワーカーが作業を始めます。モデルの推論受付順や、PMの文章に書かれた「次」という表現を工程順序の代わりにしません。
5. 後続の正式報告をPMが確認し、統合します。依存関係を使うPMは、委任レベルにかかわらず自分の全ワーカーの現在の正式報告を承認してから `finish_work` します。単なる通常メールや画面の「完了」表示だけでは、現在版の正式報告に対する承認を代用できません。

`depends_on` を省略した独立作業は従来の動作を維持します。依存待ちの間に待機確認の推論を繰り返す設計ではありません。依存関係は起動時に宣言する一方向の工程向けで、一般のグラフ編集機能ではありません。

依存関係の指定だけで報告本文が後続へ自動転送されるわけではありません。PMは担当の依頼文や具体的な引継ぎメールに、承認した先行担当ID・報告の版・入力の所在と出典を明記します。後続は必要な本文やファイルを実際に読み、不足していればPMに連絡します。これらの引用内容の正しさはモデルとPMが確認する規律です。

画面は「前工程の承認待ち」と、待っている担当名・IDを表示します。使用した承認版は作業の入力となった版であり、内容の正しさの証明ではありません。表示だけで承認や再開を操作することはなく、保存履歴は保存時点の記録です。

## 前工程が変わったら再依頼する

新しい指示などで前工程の報告が更新されたときは、その旧版に依存する後続の成果をそのまま採用しません。後続は「前工程変更・PM再依頼待ち」となり、以前の成果が失効したことを表示します。

PMは変更内容を確認し、先行の新しい正式報告を承認します。その後、親PM自身が既存の `send_message` で後続本人へ具体的な再依頼を送ります。特別な合言葉は不要ですが、何が変わり、どこをやり直すかを明記してください。アプリがこの再依頼を受理し、前工程の条件が揃い、本人が新しいターンで入力を消費してから再開します。他ワーカーのメール、掲示板への投稿、人からの追加入力だけでは、このPM再依頼を代用できません。

前工程が未承認のうちに送ったPMメールは通常の情報として届きますが、再開を許す再依頼にはなりません。必要な前工程を承認した後、新しい再依頼を送ります。

すでに完了したファイル保存などを自動的に取り消したり、旧成果物を削除したりする機能ではありません。PMは実際のファイルと版を確認し、許可された操作で必要な修正を依頼します。旧報告や監査の記録は残します。

## 手番のある反復作業と使い分ける

しりとりのように A→B→C→A と繰り返す仕事には、既存の `participant_key` / `initial_wait` / `start_ordered_work` による手番モードを使います。このモードでは本人の手番通知、候補提出、PM監査、次担当への配送をアプリが管理します。採用済みの手の訂正には `rollback_work_step` を使います。

一方向の `depends_on` と手番モードは同じ作業で併用しません。自由メールのみ、依存関係付き、手番モードという条件を混ぜて成功を評価しないでください。文字条件の一致、固定参照資料との一致、一般的な意味の正しさも別の確認です。[既存の手番と監査の説明](TEAM_COLLABORATION.md)も参照してください。

## ファイルを分担するとき

編集担当は既存の `reserve_paths` で許可済みパスを予約し、終了後に `release_paths` で自分の予約を解放します。同じEngine内の別担当が予約したパスと、その配下・上位に重なる予約や対象ツール書込は拒否されます。予約できるのは既存の書込権限が許す場所だけです。

これはアプリ内の対象ツールが確認する予約です。OS全体の排他ロックではなく、外部アプリや別プロセスの編集を禁止しません。予約を使わなかった担当を含め、すべてのファイル競合を自動発見する保証もありません。PMは担当と出力先を分け、保存時の版・SHAと最新ファイルの読み戻しを確認します。

## 報告・人への質問・失敗時の扱い

- 報告では、実施したこと、未完了、根拠、保存先と版を分けます。文章で「保存した」と述べたことと、保存記録や本人の読み戻しは別の証拠です。PMの承認も意味の正しさをアプリが保証したものではありません。
- 通常の担当間調整や前工程待ちは、PMへの連絡と `wait_for_message` で扱います。要件が本当に不足する場合や、重要な判断・承認が必要な場合は `ask_user` を使います。人専用の質問は同僚メールで解除しません。
- 失敗時は、原エラーと入力条件を残し、原因の仮説を確かめ、必要な箇所だけ修正して対応する回帰を確認します。根拠なく回数・時間を増やしたり、失敗条件を緩めて成功にしたりしません。この原因調査の品質はモデルの作業規律であり、アプリの自動保証ではありません。
- 推論・ツール・時間・自動連携の予算は共有のままです。依存待ち、訂正、スキル利用によって予算や権限が増えたり、終了した作業が再開したりすることはありません。

## SKILL.md に置く手順の例

次はユーザーの作業フォルダーへ置く手順書の本文例です。アプリへ自動インストール・読込されたスキルではありません。配置と確認は [SKILL.md の説明](SKILLS.md)に従います。

```markdown
---
name: reviewed-handoff
description: 前工程の根拠を確認してから成果物を作る共同作業。
---

1. PMは役割、入力、出力、受入基準を明記する。
2. 前工程を作り、その実IDを後工程のdepends_onへ指定する。
3. PMは現在の正式報告を読み、根拠を確認してacceptまたはreviseする。
4. 前工程が変わったら、PMは新報告を確認し後工程へ具体的に再依頼する。
5. 編集前に許可された出力先を予約し、保存後は内容を読み戻す。
6. 通常の調整はPMと相談する。本当に人が決める事項だけask_userで確認する。
7. 最終報告では実施、検証、未完了、制約を分ける。
```

スキルを読むこと、固定応答による回帰が通ること、実モデルが共同作業を最後まで正しく行うことは別の検証です。
